# ТЕХНИЧЕСКОЕ ЗАДАНИЕ
## на разработку информационной системы «StudyRoomBooking — система бронирования аудиторий»

### 1. Общие сведения
Полное наименование системы: StudyRoomBooking — информационная система бронирования аудиторий учебного заведения.
Заказчик: учебное заведение (условный). Разработчик: студентка группы 09.02.07-3ВА Сахабутдинова Маргарита Маратовна.
Основание: задание учебной практики.

### 2. Назначение и цели
Система предназначена для упрощения поиска свободных аудиторий и организации их использования.
Цели: сократить время подбора аудитории под требуемые параметры; исключить конфликтующие бронирования;
дать администратору инструменты контроля аудиторий, оборудования и броней.

### 3. Пользователи и роли
- Студент (роль user): просмотр и поиск аудиторий, просмотр занятости, создание броней, отмена своих броней, личный кабинет.
- Администратор (роль admin): управление аудиториями и оборудованием, просмотр/подтверждение/отклонение/отмена всех броней, расписание, управление пользователями.

### 4. Требования к функциям
4.1. Регистрация и авторизация: вход по логину или email; пароли хранятся в виде хешей; восстановление пароля по email через одноразовый токен (TTL 30 минут, в БД хранится только SHA-256 хеш).
4.2. Аудитории: уникальный номер, название, корпус, этаж, вместимость, тип (лекционная, компьютерная, лабораторная, конференц-зал, учебная, универсальная), статус (доступна / на обслуживании / закрыта), описание, фото.
4.3. Оборудование: каталог; связь «аудитория–оборудование» нормализована (таблица RoomEquipment с количеством единиц).
4.4. Поиск аудиторий: по дате, интервалу времени, минимальной вместимости, типу, корпусу и требуемому оборудованию; выдаются только аудитории со статусом «доступна», свободные в указанный интервал.
4.5. Бронирование: поля — пользователь, аудитория, дата, время начала/окончания, цель, комментарий, статус; статусы: ожидает подтверждения, подтверждено, отклонено, отменено, завершено. Серверная проверка конфликтов (пересечение, вложенные интервалы, границы, time_end <= time_start, прошедшие даты). Две активные (pending/confirmed) брони одной аудитории не могут пересекаться.
4.6. Расписание: таблица броней с фильтрами по дате, аудитории, статусу; занятость на карточке аудитории; расписание аудитории для администратора.
4.7. Личный кабинет: список броней со статусами, просмотр подробностей, отмена своей брони (только pending/confirmed).
4.8. Административная часть: CRUD аудиторий и оборудования, подтверждение/отклонение/отмена броней, управление пользователями (блокировка/удаление).
4.9. REST API (JWT): регистрация, вход, восстановление пароля, аудитории, оборудование, бронирования, поиск, расписание. Коды: 200/201/204/400/401/403/404/422.

### 5. Требования к надёжности
Все операции с бронями и доступ к чужим данным проверяются на сервере (защита от IDOR). Анонимный доступ только к просмотрочным страницам и API чтения.

### 6. Технологии
Python 3.11+, Django 5, PostgreSQL 15, Django REST Framework + SimpleJWT, HTML5/CSS3/JavaScript, Git.

### 7. Этапы разработки
Проектирование (ТЗ, UML, ERD) → БД и миграции → аутентификация и роли → аудитории и оборудование → поиск → бронирование и расписание → личный кабинет → админ-часть → REST API → тестирование → отчёты.
